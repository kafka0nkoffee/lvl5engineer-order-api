## What this project is and is NOT

This is the living codebase behind **The Level 5 Engineer** newsletter. It is an order
management REST API (FastAPI, port 8093) built entirely from Gherkin behavioral specifications
by Claude Code agents. The specs, findings, and editorial judgment are the human author's.
The implementation is the agent's.

**This service owns:**
- The order creation flow (`POST /orders`)
- The order status flow (`GET /orders/{id}`)
- The orchestration of calls to the payment gateway and inventory service

**This service does NOT own:**
- Payment processing logic — the payment gateway is an external dependency, not a component
- Inventory management — the inventory service is an external dependency, not a component
- User authentication — out of scope for this project entirely
- Notification delivery guarantees — the notification service is fire-and-forget by design

**If an agent is asked to "fix the payment logic" or "improve inventory management":** clarify
which layer is meant before acting. If the request concerns the order service's handling of
payment gateway responses (what to do when the gateway returns DECLINED), that is in scope.
If it concerns the payment gateway's internal processing, it is out of scope.

## Section 2: Environment discrimination

### Production resources — highest risk, specific protocols

**`ci.yml` (`.github/workflows/ci.yml`)** — Shared production resource. Any change to this
file immediately affects every contributor's merge gate. The four pipeline jobs
(`test → pact-consumer → pact-verify → can-i-deploy`) are required gates — not optional
checks, not advisory signals.
- Do not add `continue-on-error: true` to any job.
- Do not add skip conditions (`if:` clauses) that exempt branches from any job.
- Do not reduce the dependency chain between jobs.
- Disabling or weakening any of the four pipeline jobs is equivalent to removing a production
  safety gate. If CI is consistently failing and you believe the cause is a flaky test rather
  than a real breakage, surface the issue to the human — do not work around it in the YAML.

**`main` branch** — Production equivalent. Pushing directly to `main` bypasses the four-job
pipeline and is equivalent to a production deployment without testing. All changes go through
a branch and a PR that clears all four CI jobs.

**`pacts/` directory** — Derived artifact. These files are generated by running the Pact
consumer tests (`pytest tests/pact/test_payment_gateway_consumer.py
tests/pact/test_inventory_service_consumer.py`). Never edit them manually. A manually-edited
pact file creates a consumer contract that no consumer code actually holds, which means
provider verification passes against a fictional contract.

### Test resources — may be modified as needed

- Local ports 8091, 8092, 8093, 8094 — used by the mock servers during test runs
- Feature branches — changes here do not affect the shared merge gate until a PR is opened
- All files under `tests/` and `wiremock/` (with the stub modification protocol below)

## Section 3: Architectural invariants

These properties must remain true across all future changes to this system. They are not
implementation preferences — they are load-bearing design decisions. Violating an invariant
produces a failure that passes all behavioral tests and manifests in production.

**Before modifying any aspect of the order creation flow in `app/main.py`, read the
invariant that applies to that aspect.**

---

**Invariant 1: Inventory must be checked before the payment gateway is called.**

Consequence: If violated, the payment gateway is charged for orders that cannot be
fulfilled. Every out-of-stock order results in a payment charge that must be reversed through
the gateway — adding a reversal flow that does not currently exist in this service.

Currently enforced by: Gherkin Scenario 3 in `tests/features/order_creation.feature`
("the payment gateway is never called for out-of-stock items"). Note: this Gherkin scenario
enforces the *outcome* (no payment for out-of-stock), not the *mechanism* (inventory checked
first). A concurrent implementation that checks inventory and payment simultaneously, then
cancels the payment call if inventory fails, satisfies the Gherkin scenario while violating
this invariant — because the gateway receives a charge request before the inventory result
is known.

ADR reference: ADR-001 (planned — Issue #16)

---

**Invariant 2: The notification service call must remain asynchronous (fire-and-forget).**

Consequence: Making the notification call synchronous couples order confirmation latency
to notification service availability. When the notification service is slow or unavailable,
order confirmations are delayed or blocked — a much worse failure mode than a missed
notification.

Currently enforced by: Convention (`_fire_notification()` in `app/main.py` uses a daemon
thread; all exceptions are caught and discarded). There is no test that asserts this call
is asynchronous.

Important: "More reliable notifications" is not a valid reason to make this call synchronous.
Making it synchronous trades notification reliability for order confirmation reliability.
This project has made the explicit choice that order confirmation reliability is the
higher-priority property.

ADR reference: ADR-002 (planned — Issue #16); see also `findings/issue-07-scope-problem.md`

---

**Invariant 3: The Pact consumer contract is the authoritative source for API shape between
this service and its dependencies.**

Consequence: If a stub file is changed to return a different field name or shape, and the
Pact contract is not updated to match (with consumer consent), provider verification will
fail in CI. If the Pact contract is modified directly to match a stub change without running
consumer tests, the contract no longer reflects what the consumer code actually expects.

Currently enforced by: The `pact-verify` job in CI; the `can-i-deploy` check.

The correct flow for any stub response change:
1. Change the implementation
2. Run `pytest tests/pact/test_*_consumer.py -v` — this regenerates the pact files
3. Run `pytest tests/pact/test_provider_verification.py -v` — this verifies against the new contract
4. If verification fails, the implementation must be reverted

ADR reference: `findings/issue-04-pact-contract-testing.md`

---

**Invariant 4: The payment retry cap is 2 total attempts (1 original + 1 retry), not 2
retries on top of the original attempt.**

Consequence: If interpreted as "2 retries in addition to the first attempt," worst-case
payment timeout behavior becomes 3 attempts × 5 seconds = 15 seconds, violating the 12-second
response window specified in Gherkin Scenario 5. The Gherkin scenario uses the wording "no
more than 2 charge requests total" — "total" includes the original attempt.

Currently enforced by: `tests/features/order_creation.feature` Scenario 5 (after Issue #8
fix: "the payment gateway receives no more than 2 charge requests total").

ADR reference: `findings/issue-08-spec-audit.md` (the fix that resolved the original
ambiguity of "not retried more than 2 times")

---

**Invariant 5: The mock server lifecycle is owned by the pytest session fixtures, not by
external processes.**

Consequence: If any process outside the pytest session attempts to start mock servers on
ports 8091/8092/8093/8094 before the session fixtures run, the fixtures will fail with
`OSError: Address already in use`. The `ci.yml` must not start mock servers in a separate
step before invoking pytest — the session fixtures in `tests/steps/conftest.py` already
handle this.

Currently enforced by: Convention; documented in `findings/issue-06-cicd-guardrails.md`.

ADR reference: `findings/issue-06-cicd-guardrails.md` (port conflict finding)

## Section 4: External service contracts

### Payment gateway (port 8091)

**What this service sends:**
```
POST /payments/charge/{scenario}
Body: {"order_id": "<uuid>", "amount": <float>, "items": [<sku>, ...]}
```

**Load-bearing response fields** (must be present — Pact contract enforces these):
- `status`: "ACCEPTED", "DECLINED", or absent on timeout — drives the order outcome
- `transaction_id`: Present on ACCEPTED — stored in the order record
- `amount`: Present on ACCEPTED — echoed back for verification

**Failure modes this service handles:**
- DECLINED response (gateway returns 402 or `"status": "DECLINED"`) → order returns
  `PAYMENT_FAILED` (402), inventory reservation is released
- TIMEOUT (no response within `PAYMENT_TIMEOUT_SECONDS=5`) → retry once (2 total attempts
  max), return `PAYMENT_PENDING` (202) with `inventory_hold_minutes: 15`

**Failure modes intentionally NOT handled:**
- Gateway returning 5xx status codes → treated identically to timeout (not specifically
  handled; may produce undefined behavior)
- Gateway returning malformed JSON → will raise an unhandled exception; no recovery logic

**Design decisions driven by this service's behavior:**
- The 2-total-attempt cap (Invariant 4) was set so worst-case latency (2 × 5s = 10s) fits
  within the 12-second Gherkin response window. Increasing `MAX_PAYMENT_RETRIES` or
  `PAYMENT_TIMEOUT_SECONDS` without recalculating this window violates the scenario contract.

---

### Inventory service (port 8092)

**What this service sends:**
```
POST /inventory/check/{scenario}
Body: {"items": [<sku>, ...]}
```

**Load-bearing response fields** (Pact contract enforces these):
- `availability`: "ALL_AVAILABLE", "OUT_OF_STOCK", or "PARTIAL" — drives the order path
- `available_items`: List of available SKUs (required for PARTIAL responses)
- `unavailable_items`: List of unavailable SKUs (required for OUT_OF_STOCK and PARTIAL)

**Failure modes this service handles:**
- OUT_OF_STOCK → order returns `UNAVAILABLE` (409); payment gateway never called (Invariant 1)
- PARTIAL → order returns `PARTIAL_UNAVAILABLE` (207); payment gateway never called

**Failure modes intentionally NOT handled:**
- Inventory service timeout → not handled; will propagate as an unhandled exception
- Inventory service returning an unexpected availability value → not handled

**Design decisions driven by this service's behavior:**
- Inventory is checked BEFORE payment because inventory failure must prevent the payment
  gateway from being called. This ordering is Invariant 1. Do not optimize away this ordering.

---

### Notification service (port 8094)

**What this service sends:**
```
POST /notifications/order-confirmed
Body: {"order_id": "<uuid>", "total": <float>}
```

**Load-bearing response fields:** None. This call is fire-and-forget. The response is
discarded in all cases.

**Failure modes this service handles:**
- ALL failure modes — 4xx, 5xx, timeout, connection refused — are handled by discarding the
  result. The daemon thread catches all exceptions and logs nothing. This is intentional.

**Failure modes intentionally NOT handled:**
- Successful delivery confirmation — the order service does not verify that the notification
  was delivered. This is by design.

**Design decisions driven by this service's behavior:**
- This call is asynchronous because coupling order confirmation to notification delivery
  would mean a notification service failure blocks order confirmation. This is Invariant 2.
- Any agent asked to "improve notification reliability" or "ensure notifications are
  delivered" must read Invariant 2 before acting. Making this call synchronous is not
  an improvement for this system — it is a trade-off that this project has explicitly rejected.

## Running the test suite

```bash
# Install dependencies
pip install -r requirements.txt

# Run all Gherkin scenarios (11 tests)
pytest tests/steps/ -v

# Run Pact consumer and provider tests (4 tests)
pytest tests/pact/ -v

# Run can-i-deploy check
python3 scripts/can_i_deploy.py
```

All 15 tests must pass before any session is considered complete. If any test fails
at the start of a session, diagnose and fix the failure before beginning new work.

## Documentation protocol — findings/

**At the start of every session, create a new file in `findings/` named:**

```
findings/issue-{N}-{short-topic}.md
```

Do not append to existing findings files. Each session gets its own file.

**After creating the file, add a row to `findings/README.md`.**

**Also update the root `README.md`:**
- Change the `_Repo up to date with Issue #N_` line to the current issue number
- Add the new findings file to the project structure tree
- Add a new section describing what changed this session

Use the following structure for each entry within the findings file:

```markdown
## [Short title of what was attempted]

**Date:** YYYY-MM-DD
**Status:** ✅ Worked | ❌ Failed | ⚠️ Partial

### What I tried
### What happened
### Root cause
### The fix
### Why this matters
```
